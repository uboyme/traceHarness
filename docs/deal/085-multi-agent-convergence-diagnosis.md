# 085：助手为什么永远跑到被打断——multi 的收敛与成本诊断

日期：2026-09-22。数据来自[记录 084](084-fold-maturity-fixes.md) 的 14 轮真实运行，
本记录不重复那些修复，只回答一个它没回答的问题：**同一个题目，multi 为什么这么慢。**

结论先写：**慢的主因不是并行做得差，是助手不知道什么时候该停。**

## 1. 助手 10 轮里只有 1 次自己结束

| 结束方式 | 次数 |
|---|---|
| 撞墙钟被取消 | 5 |
| 出错（传输 / 记账 / 上下文） | 4 |
| **自己完成** | **1**（`c4e-run`） |

关键不在比例，在那 5 次取消的**墙钟读数**：24.0、25.0、25.1、25.1、25.4 分钟，
上限 25 分钟。**一次不落全部顶满。** 这不是"有时候来不及"，是"从不提前结束"。

`c4c-run`（10.8 分钟）和 `c4k-run`（18.2 分钟）提前结束是因为报错，不是因为做完了。

## 2. 给它信息它不看，给它建议它不听

助手工具表里**本来就有** `inspect_investigation_budget`，可以随时查自己还剩多少额度。
实际使用：`c4p-run` 37 步里 **1 次**，`c4-run` 50 步里 **2 次**。

084 §7.1 记录的另一个事实同向：到达收尾线、工具已全部撤走之后，它仍然发出 6 个读回调用，
全部被拒，白花 30.4 秒，然后撞墙钟。**提示词层面的收敛劝导已经被证伪过一次。**

这条排除了一整类方案：靠说服让它自觉收敛。084 §5 的"撤工具"是在**人为制造**一个收敛点，
因为它自己造不出来。

## 3. 根因：它的交付物没有完成判据

助手的 assignment 是"产出一份带原文引用的调查报告"。
"资料读够了没有"**没有下限**——多读一个文件总是显得更负责。

对照之下主方有判据：补丁写完、测试跑过，就可以交。
`c4p-run` 里主方读 23 个文件就动手了，助手读了 68 个还在读。

这也解释了为什么 084 里修了九个缺陷仍然一次次卡在助手交付上：
**那是在给一个没有终点的过程加护栏。**

## 4. 第二笔成本：等待要过模型

`c4p-run` 主方为"报告好了吗"单独花掉：

| | |
|---|---|
| 步数 | 6（本 Step 唯一的工具调用就是 `collect_investigation`） |
| 模型时间 + 工具等待 | **4.2 分钟** |
| token | **159,852** |
| 结果 | 5 次 pending，1 次 failed |

**问一句"好了吗"要花约 2.7 万 token。** 因为 `collect_investigation` 最多等 30 秒就返回，
而助手要跑 25 分钟，于是主方只能反复问；每问一次都是完整 Step：
重发整个对话 → 过模型 → 等 30 秒 → 返回 pending → 再来。

这是 14.3.19 `dispatch_and_continue` 的代价：它让主方能边等边干活，
代价是"等"这个动作本身要过推理。等待式 `await_report` 本来是阻塞的，
并发模式下没有对应的长等待。

## 5. 第三笔：七成产出是没人看的推理

`c4p-run`：

| | 生成 token | 其中推理 |
|---|---|---|
| 助手 | 49,001 | **36,469（74%）** |
| 主方 | 30,694 | **19,876（65%）** |

29 分钟的整轮里，约 14 分钟在生成永远不进对话的思考。
这条与架构无关，是模型选择；但它是单项影响最大的因素。

| | 助手 | 主方 |
|---|---|---|
| 墙钟 | 25.1 分钟 | 28.8 分钟 |
| 等模型 | 12.3 分钟（49%） | 7.5 分钟（26%） |
| 调用次数 | 38 | 36 |

| 工具 | 中位 |
|---|---|

## 7. 三项提案（均**未实施**，需要授权）

按性价比排序。每项都给出它要解决的具体观测。

### 7.1 增量交付：边查边交，不在最后憋一份报告

**现状**：助手的工具只有读文件、查预算、取回折叠内容
（`src/traceh/product/runtime.py` 的 `READ_TOOL_IDS + INVESTIGATOR_BUDGET_TOOLS + OUTPUT_TOOL_IDS`）。
**它没有任何办法把发现写下来**，全部交付压在最后一条消息里。

一次解决四个已观测问题：

| 现在 | 改后 |
|---|---|
| 最后生成约 12,000 字 → 165 秒 → 超过 Provider 超时（084 §8 run14） | 每次几百字，不触发超时 |
| 任何时刻被取消 = 交付为零（10 轮里 9 轮如此） | 任何时刻被取消 = 已有发现仍在 |
| 折叠收走它要逐字引用的原文 → 反复取回（084 §6） | 引用在发现时固化，折叠不再伤它 |
| "还要不要再读一个文件"没有下限 | "待答问题清空"是可判定的终点 |

最后一行是本记录的核心：**"理解够不够"没有判据，"待答问题还剩几个"有。**
这也正是主流 subagent 能收敛的原因——它们的任务通常是"找到 X"而不是"理解 Y"。

设计边界（必须遵守）：增量发现是**持久事实**，应沿既有 Effect/Artifact 主线落盘，
不得新建第二份事实源，不得引入可变的"模型记忆"代替原始事件。

### 7.2 并发模式下的长等待

宿主**知道**助手还剩多少额度（`Supervisor.report` / Budget 账本）。
让 `collect_investigation` 在并发模式下按已授权时长阻塞，而不是切成 30 秒一片。
预期效果：§4 的 159,852 token 与 6 个轮询 Step 降一个数量级。

边界：等待时长必须来自已授权额度推导（参照 14.3.24 / ADR-0079 的等待式做法），
不得写成常量；取消仍只取消调用方的等待，不取消助手。

### 7.3 换模型或关闭推理通道

§5 的 71% 是单项最大因素。属实验条件，不是代码改动。

## 8. 一条方法论结论

run4 之后**九轮没有一次死于上下文**，每轮死在不同的 owner 上
（监督、传输、失败分类、预算记账、提示与回执，见 084 §8.1）。
一条四十分钟、两个角色、约百次调用的长链，一次观测只能暴露一个缺陷，
因为前一个致命故障会掩盖它后面的全部。

因此：**上下文机制的验收不应以端到端任务成功为因变量。**
它已经有离线对照、每请求指标和逐项反向验证。
要取得固定 Verifier 的裁决（14 轮一次未达），应另走 single 模式同题路径，
去掉助手那一整条失败链；这同时也给出 single/multi 的成本对照，
而那本来就是本项目要测量的东西。
