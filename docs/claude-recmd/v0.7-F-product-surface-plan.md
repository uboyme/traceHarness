## 1. 四条核心原则

### 原则一：宿主渲染权威面，模型只做解释

任何**用户据以决策**的内容——改动文件列表、验证结论、review id、approval digest、Token 数、推广前后 revision——必须由宿主从持久事实渲染，**不得出现在模型消息里**。

强制手段不是叮嘱模型，而是**让模型拿不到**：

> 模型上下文中永远不包含 approval digest、artifact sha256、推广的 expected-old / new revision。

可测：为 chat 模型构建的任何请求中，这些字面量都不出现。

配套的用户信号必须准确表述为：

> **没有 ProductTask 面板，就没有发生 ProductTask、Workspace 或 Promotion 变更。**

（不能说"没有面板就没有任何持久事实"——普通聊天本身就在写 Session Event。）

### 原则二：批准与推广确定性执行；启动可由自然语言确认，但必须先回显

分成两级，因为它们的爆炸半径不同：

**不可协商的一级（批准 / 推广）**：`/approve <digest>` 由宿主确定性识别，模型**永远无权批准**，也不得配置跳过。

**可自然语言的一级（启动执行）**：启动只会拉起隔离执行——它不能批准、不能推广、不能越过预算上限、只有 coder 拿到可写 worktree。因此允许模型在用户自然说"开始"、"就用 multi" 时确认 Proposal。

但**回显不可省**：启动前必须先渲染一屏宿主 preflight，显示解析后的模式及其来源、拓扑、**预算上限**、workspace 与解析后的 base commit、verifier plan、promotion target。用户看到的是宿主算出来的事实，不是模型的转述。

模型的 Tool：

```
propose_task(requirement: str, mode_hint: "single" | "multi" | "auto" | null) -> proposal_id
```

`mode_hint` 只是**提示**，进入 preflight 后仍按第 5 节的规则解析（显式提示不调用 Router；`auto` 或缺省才路由），并在面板上标注来源。模型无法借此绕过 Router 的收窄合同，因为它给不出预算、路径、Provider、Verifier 或 Git 目标。

`/task`、`/start` 保留为精确操作入口，**不是日常必经路径**。

### 原则三：只有一个执行引擎

`single` 是**只有一个 AgentTask 节点的 Workflow**，不是"现有单 Agent 主线"。single 与 multi 走完全相同的安全门与生命周期状态机。

| 档 | 是什么 | 安全门 | 持久痕迹 |
|---|---|---|---|
| 纯聊天 | 问答、讨论 | 无 | 仅 Session |
| Task / single | 单节点 Workflow | 全套 | Session + ProductTask + Workflow |
| Task / multi | parent → reviewer → coder | 全套 | 同上 |

### 原则四：生命周期完整且**诚实**

- `completed` / `rejected` / `cancelled` / `abandoned`：持久终态；
- `interrupted`：**派生**状态（有 `task-started`，但 Workflow 投影显示节点有 start 无 terminal）。

关键的诚实性约束：

- **同进程、仍被产品服务拥有的运行**可以取消——取消调用方任务，E 会收敛节点，然后写 `cancelled`，此时收敛证据可以断言为 0；
- **硬中断（Ctrl-C / 进程死亡）之后不能这样承诺**。E 没有公开的 Workflow cancel API，宿主也不知道那个节点留下了什么（Agent 认领、预算占用、worktree）。这种 Task 保持 `interrupted`，**只允许 `/inspect`**；
- 若用户要把它移出活跃列表，只能写 `abandoned`，并在面板上明说 **"底层资源未被证明已释放"**。不得伪装成 `cancelled`，不得偷偷释放状态未知的 Workspace / Budget。

## 2. ProductTask 事实模型

### 为什么需要新流

`WorkflowService.resume(run_id, definition)` 要求重建**完全相同**的 definition。而 definition 只保存 binding id，真正的装配（AgentSpec、verifier plan、promotion target、budget、workspace commit）在宿主一侧。要在第二天安全恢复，必须能证明**装配也没变**。这些都不属于任何已有域。

ADR 必须论证它**不是第二事实源**：只记录产品级身份与控制决定，只保存指向其它域的**引用与摘要**，不复制任何其它域的状态。

### 流与事件

- 流：`product-task:<task_id>`，每 Task 一条；枚举用 `list_streams(prefix="product-task:")`
- `task_id` **由宿主生成**（非模型、非用户），`run_id == task_id`
- schema 从 `1` 开始；未知版本拒绝而非迁移

| 事件 | 载荷 | 说明 |
|---|---|---|
| `product/task-opened` | `task_id`、`origin_session_id`、`origin_message_id`、`requirement_digest`、`profile_digest`、`assembly_digest`、`source_base_revision`、`requested_mode`、`mode_source` | 需求文本不复制，只存引用 + 摘要 |
| `product/task-routed` | `router_agent_id`、`router_session_id`、`resolved_mode`、`reason`(≤200 字符，仅展示) | 仅 `auto` 时出现，且**在 opened 之后** |
| `product/task-started` | `mode`、`definition_hash`、`workflow_run_id` | 写入后 Workflow 才可启动 |
| `product/task-awaiting` | `review_id` | 停在 Approval 屏障时写入 |
| `product/task-settled` | `outcome`(completed/rejected/cancelled/abandoned/failed)、`promotion_id`(仅 completed)、`resources_proven_released`(bool)、`failure_code` | 唯一终态；`abandoned` 时该 bool 为 `false` |

`interrupted` **不写事件**——它是派生的。写它会造出第二事实源，并让"谁来写"变成无解问题（进程已经死了）。

### Assembly Digest（本轮新增，关键）

`assembly_digest` 是对**解析后**装配的 canonical JSON SHA-256，至少覆盖：

- 每个 preset 解析出的 AgentSpec 关键字段（preset、capability_grants）；
- 七维完整 `BudgetLimits`（task 与 router 各一份）；
- verification plan 的 `verifier_definition_digest`（D2 已有）；
- promotion target 的 id 与 fingerprint（D2 已有）；
- workspace `source_id` 与**解析后的 commit**。

理由：profile 文件没变，不代表这些 id 指向的宿主对象没变。只绑 `profile_digest` 会出现"definition hash 相同，实际装配已经变化"。

**恢复规则**：`profile_digest` 或 `assembly_digest` 任一不符 → 拒绝继续，不静默用新装配重建。

### Reader 必须交叉验证

`ProductTaskReader` 每次 fresh-read，并与真实域交叉核对，不能只相信引用字段：

- `origin_message_id` 在该 Session 中存在且 `requirement_digest` 相符；
- `workflow_run_id` 的投影与 `definition_hash` 相符；
- `review_id` 在 Promotion Ledger 中存在且 `passed`；
- `promotion_id`（若有）确实指向该 approval。

任一不符 → 结构化失败，不猜测。

### 状态机

```
opened ─(auto)→ routed ─→ started ─→ awaiting ─→ settled(completed)
                                  ├────────────→ settled(rejected)
                                  ├────────────→ settled(cancelled)    ← 仅同进程收敛
                                  ├────────────→ settled(abandoned)    ← 资源未证明释放
                                  ├────────────→ settled(failed)
                                  └─(派生)─────→ interrupted            ← 无事件
```

严格性与 E 同级：序号连续、schema 已知、类型已知、每类事件 key 集合精确匹配、终态后不接受任何事件、`task-awaiting` 不得早于 `task-started`、`task-routed` 不得早于 `task-opened`。

## 3. Profile 契约

定长 schema，**不含任何图结构**。

```jsonc
{
  "profile_version": 1,
  "provider": "openai-compatible",
  "model": "configured-model",
  "presets": {
    "parent":   { "preset": "analyst",  "capability_grants": [] },
    "coder":    { "preset": "coder",    "capability_grants": [] },
    "reviewer": { "preset": "reviewer", "capability_grants": [] }
  },
  "workspace": { "source_id": "project-main", "revision": "main" },

  // 七个维度全部显式，null 表示宿主明确选择不限制该维度
  "budget": {
    "task": {
      "max_tokens": 60000, "max_steps": 200, "max_tool_calls": 400,
      "max_wall_milliseconds": 900000, "max_children": 3,
      "max_depth": 1, "max_processes": 3
    },
    "router": {
      "max_tokens": 2000, "max_steps": 2, "max_tool_calls": 0,
      "max_wall_milliseconds": 30000, "max_children": 0,
      "max_depth": 0, "max_processes": 1
    }
  },

  "verification_plan_id": "fixed-python-quality",
  "promotion_target_id": "local-managed-main",
  "model_input_limits": {
    "max_report_bytes": 65536,
    "max_patch_bytes": 262144
  },
  "confirm_start": "natural"   // natural | explicit
}
```

- 缺任何一个预算维度 → 加载失败。不接受省略。
- `"revision": "main"` **只用于 preflight 展示**；`task-opened` 必须绑定重新解析出的精确 commit（`source_base_revision`）。
- `confirm_start: natural` 允许模型确认启动（原则二），`explicit` 要求 `/start`。**`/approve` 那道门与本项无关，永不可配。**
- Profile 不能定义 verifier 命令本身，只能按 id 选择宿主已冻结的 plan。

## 4. 固定拓扑

写死在代码里，不由配置决定。

**single**（3 节点）：

```
coder(capture=True) → verification(artifact=coder) → approval(review=verification)
```

**multi**（5 节点，线性）：

```
parent(capture=False) → reviewer(capture=False) → coder(capture=True)
    → verification(artifact=coder) → approval(review=verification)
```

**Reviewer 放在 coder 之前，这是本轮的重要修订。** 原先排在 coder 之后是设计错误：E 的 AgentTask 只证明"消息完成"，不理解 Reviewer 的"通过 / 不通过"；Reviewer 之后没有任何 Agent 消费它的意见，固定 Verifier 也不读它——那样它只是一个昂贵的旁观者。

现在的分工是可消费的：

- `parent` 提出计划；
- `reviewer` 只读检查计划、风险与边界；
- `coder` 的 message binding 由宿主 resolver **fresh-read parent 与 reviewer 的 durable report** 渲染而成，因此意见真的进入了执行；
- 固定 Verifier 检查最终 Patch。

若要 Reviewer 审查 Patch 本身，需要结构化 verdict 与 coder 修订循环——超出当前最小固定 DAG，留给后续版本。

**模型输入必须有界**：所有跨 Agent 的注入（durable report、Patch 片段）由宿主按 `model_input_limits` 截断，采用固定编码规则，并在注入内容中留下**截断证据**（原始字节数 + 是否截断）。不得把完整 Artifact 无界塞进模型。

只有 `coder` 拿 `WorkspaceAccess.WRITABLE`；`parent` / `reviewer` 只读。

v0.7-F 不使用 Map/Join。它们在 E 中仍存在且受测，只是这两个出厂拓扑用不到——ADR 需写明，避免被读成"E 的能力缩水"。

## 5. Router 契约

- 仅当解析后的模式为 `auto` 时调用；显式 single/multi **不调用 Router**。
- **Router 是一个真实 Agent，拥有自己的 Session 与 Budget Account**（走 profile 的 `budget.router`）。普通只读 Session 不会自动进入 Budget Ledger——`_require_agent_session` 决定了这一点，所以"普通 Session 自然计费"的想法是错的。
- Router **不持有任何服务句柄**：它是 (需求文本) → 枚举 的函数，不注入 Supervisor、WorkflowService、PatchPromotionService、WorkspaceService。
- 输出必须是严格 JSON，且只接受两个值：

```json
{ "mode": "single", "reason": "localized change with a deterministic verifier" }
```

- `reason` 截断到 200 字符，**仅供展示**，不参与任何控制判断。
- 格式错误 / 超时 / 取消 / 值不在枚举内 → **结构化失败，不回退到任何模式**，不重试。
- **路由前必须验证 single 与 multi 两套装配都可用**（路由前还不知道会去哪一边）。
- Router 会创建一个 Agent，因此"single 不创建 child"这类验收断言必须把 router agent 与 task agent 分开计数。

## 6. 执行顺序（本轮修订，必须固定）

原稿把 Router 成本显示在"没有持久事实"的 preflight 屏上，这是矛盾的：Router 一旦调用就已产生 Session 与 Budget 事实，而 Task 尚未存在，这笔成本无法可靠归属。

固定顺序：

```
自然聊天
  → 临时 Proposal（进程内 UI 状态，不是 Event，退出即消失）
  → 装配预检（只读、无模型、无成本）
  → 用户确认开始（自然语言或 /start，取决于 confirm_start）
  → 写 product/task-opened      ← Task 从这里开始存在
  → （auto 时）Router Agent + Session + Budget
  → 写 product/task-routed
  → 写 product/task-started
  → Workflow 执行
```

因此：**Proposal 屏不显示尚未发生的 Router 成本**；路由结果与成本在 Task 开启后的权威面板上展示，并可靠归属于该 Task。

## 7. CLI 表面

### Proposal 的存放

Proposal 是**明确的进程内临时 UI 状态**，不是持久事实，进程退出即消失。`chat.py` 目前没有这个概念，需要新增；退出后没有"待启动的提议"可恢复，这是有意的。

### 命令

| 命令 | 作用 |
|---|---|
| `/task single\|multi\|auto <需求>` | 精确入口，`mode_source=user` |
| `/start` / `/start single\|multi` | 执行当前 Proposal（`confirm_start: explicit` 时必经） |
| `/drop` | 丢弃 Proposal（无持久痕迹） |
| `/tasks` | 列出未终结 Task 及状态 |
| `/show [task_id]` | 渲染权威面板 |
| `/diff [path]` | 从 Artifact 渲染真实 diff |
| `/approve <digest>` | 精确摘要批准，宿主确定性校验 |
| `/reject [task_id]` | 写 `rejected`，释放 worktree，保留 Artifact |
| `/cancel [task_id]` | **仅对本进程拥有的运行**：收敛后写 `cancelled` |
| `/resume <task_id>` | 仅对 `awaiting_approval` 有效 |
| `/inspect <task_id>` | `interrupted` 的唯一出路（只读） |
| `/abandon <task_id>` | 把 `interrupted` 移出活跃列表，写 `abandoned` 并标注资源未证明释放 |
| `/cost [task_id\|session]` | 从 Budget Ledger 渲染，标注 `UsageQuality` |

`/resume` 与既有 session `resume` 子命令语义不同，帮助文本必须区分。

### 面板

集中在 `src/traceh/product/panels.py`：只接受来自持久事实的 DTO，**不 import 任何 provider / 模型响应类型**，是 approval digest、artifact sha256、推广 revision 的**唯一**输出位置。

三屏必须呈现：

- **preflight**（无成本）：需求、模式及**来源标注**、拓扑与节点数、七维预算上限、workspace source 与**解析后的 base commit**、verifier plan、promotion target；
- **awaiting approval**：artifact id 与 sha256、变更文件与增删行数、每条 verifier 命令的 exit code / 耗时 / 输出字节数、review id、target ref 与 expected-old、approval digest；
- **settled**：CAS 前后 revision 与结果，以及收敛证据（active agents / open turns / open steps / process slots / pending budget reservations / remaining worktrees）。`abandoned` 时此处必须明示"未证明为零"。

### 成本口径

分列 `routing` / `execution`（按 Agent 拆分）/ `task total`，标注 `UsageQuality`，并明确声明**不含本次会话中不属于 Task 的对话消耗**（另由 `/cost session` 给出）。

### 并发

同一 chat session **至多一个活跃 Task**；已有活跃 Task 时的新提议被拒绝并指向该 Task。

## 8. 阶段分解

### F0 — 合同冻结（ADR-0032）

交付：`docs/adr/0032-*.md` + `src/traceh/api/product.py`（冻结 DTO 与 Protocol，无实现）。

冻结：四条核心原则、ProductTask 流与事件、**Assembly Receipt / assembly_digest**、状态机（含 `interrupted` 派生与 `abandoned` 诚实终态）、Profile schema（七维预算、commit 解析规则、`model_input_limits`）、两个固定拓扑（reviewer 在 coder 之前）、Router 契约（真实 Agent + Budget Account）、第 6 节执行顺序、命令集与三屏面板、成本口径、并发上限、**Benchmark 通路决定**。

ADR 必须写明：为什么 ProductTask 不是第二事实源；为什么 single 也走全套安全门；为什么 F 不用 Map/Join 但 E 能力未缩水；为什么硬中断只能 `abandoned` 不能 `cancelled`。

**F0 是决定，不是实现**：ADR 不得声称已实现。

### F1 — ProductTask Ledger 与装配解析

`product/models.py`、`events.py`、`projection.py`、`errors.py` + Profile / Registry 解析 + `assembly_digest` 计算 + `ProductTaskReader` 交叉验证。

不含 chat 接线，不含 Router，不含拓扑执行。测试聚焦：流严格性、状态机、assembly digest 覆盖面、交叉验证失败路径、恢复拒绝（profile 或 assembly 变化）。

### F2 — Chat 接线、Proposal、Router、拓扑、面板

`propose_task` Tool、临时 Proposal 状态、第 6 节顺序、Router（真实 Agent + Budget）、两个固定拓扑与有界注入、`panels.py`、全部命令。

### F3 — 真实模型正向验收

single / multi / auto 三条正向链路，用一次性 bare 仓库（不碰任何真实远端）：

1. `/task single` 不创建 task child（**router agent 单独计数**）；
2. multi 确实是 parent → reviewer → coder，且只有 coder 可写；
3. coder 的输入确实包含 parent 与 reviewer 的 durable report（且带截断证据）；
4. auto 的路由结果被严格解析并进入对应拓扑；
5. terminal 后捕获 immutable Patch；
6. 固定 Verifier 通过；
7. 人工精确摘要批准；
8. 显式 Git ref CAS 推广；
9. 收敛可判定：六项计数全为 0。

**否定性质不在这里证明**——"Auto 不能改变预算/路径/批准权限"由 F2 的确定性测试与架构守卫承担。

### F4 — 用 ProductTask 重构 `traceh eval`

**F0 已冻结的决定，不再留给实现者**：

- 复用并重构现有 `traceh eval`，**不新增第二个 Benchmark CLI**；
- 项目 pre-1.0 且不保留历史兼容，**直接替换旧 manifest schema**，旧 schema 明确拒绝，**不保留适配层**；
- 新 Eval **调用真实 ProductTask 表面**，不再绕过它直接构造 Runtime。

2–3 个固定任务；控制变量：同 provider/model、同源码 commit、同需求、同 verifier、同预算、全新 Session / 数据目录 / Workspace。

指标与**持久事实来源**：成功与否 ← 固定 Verifier（不接受模型自称）；Token 与证据等级 ← Budget Ledger 的 `UsageQuality`；调用次数 / Step / Tool ← Session Event Log；child 数量 ← Agent Directory；模式与来源 ← ProductTask 流；预算拒绝 ← Budget Ledger；耗时 ← 宿主单调时钟。

**计时口径**：分列 `active elapsed` 与 `approval wait`，benchmark 中以编程方式立即批准并在报告中标注。`多 Agent 累计工作时长` 从事件日志推导（Turn 时长求和），不得由脚本自行记账。

**诚实性**：`auto` 不是独立第三组（退化为 single 或 multi，唯一可测的是路由开销与解析严格性）；结果标注为**单次描述性观测**，不声称统计显著性；不得据 2–3 个任务宣称某模式普遍更优。

## 9. 架构守卫（F2 起可测，缺一不可）

1. `AgentLoop` / `AgentRuntime` / `ProcessAgentSupervisor` / `PluginManager` 不 import `traceh.product`，四文件字节不变；
2. `traceh.product` 不 import `runtime.agent_loop`、`runtime.agent_runtime`、`supervision.supervisor`、`supervision.execution`（`durable_log_identity` 按名放行）、`plugins.manager`；
3. `traceh.workflow` 不 import `traceh.product`（依赖单向）；
4. Router 模块不 import 任何服务类型；
5. `panels.py` 不 import provider / 模型响应类型；
6. `propose_task` 输入 schema 只有 `requirement` 与 `mode_hint`，不含预算、路径、Provider、Verifier、Git 目标；
7. `approve` / `promote` / `compare_and_swap` 的调用点集合被 AST 断言锁定在产品服务的确定性命令路径上；
8. 产品域只新增 `product-task:` 前缀的流；
9. 所有被组合服务通过 `durable_log_identity` 校验为同一条 log；
10. **模型上下文不含机密面**：为 chat 模型构建的请求中不出现 approval digest、artifact sha256、expected-old / new revision。

## 10. 必需的反向验证（每项恢复后 grep 确认无残留）

1. 把 digest 放进模型上下文 → 守卫 10 变红；
2. 让 `propose_task` 接受预算或 Git 目标 → 守卫 6 变红；
3. Router 失败时回退到 single → 不回退测试变红；
4. 允许模糊同意触发推广 → 精确批准测试变红；
5. 允许 `interrupted` 走 `/resume` → 恢复边界测试变红；
6. 忽略 `assembly_digest` → 恢复拒绝测试变红；
7. 把 Router 移回 `task-opened` 之前 → 成本归属测试变红；
8. 让 `/abandon` 声称资源已释放 → 诚实性测试变红。

## 12. 给实施方的注意事项

1. **推广是宿主动作**：Approval 节点只确认批准存在；`promotion.promote(approval_digest=...)` 由产品层在 run 到达 `completed` 之后调用。不要塞进 Workflow。
2. **resume 必须重建完全相同的 definition**，且 `profile_digest` 与 `assembly_digest` 都要相符才允许继续。
3. **不要复制其它域的状态**：ProductTask 只存引用与摘要。
4. **`interrupted` 不写事件**，是派生的。
5. **不要承诺你无法证明的清理**：硬中断只能 `abandoned` 并标注资源未证明释放。
6. **并发测试用 Event / Gate**，不用任意 `sleep()`。
7. **失败要保留完整集合**：复用 `traceh.concurrency` 的 `combine_failures` / `informative_failure`，不新写一份。
8. 每个反向验证做完必须恢复并 grep 确认无临时补丁残留。

## 13. v2 相对 v1 的修订

| # | 修订 | 理由 |
|---|---|---|
| 1 | 启动可由自然语言确认（`confirm_start: natural`），但 preflight 回显不可省；批准仍只能确定性执行 | v1 强制 `/start` 使产品退化为命令拼接；启动的爆炸半径确实低于批准 |
| 2 | Proposal 明确为进程内临时 UI 状态，非 Event | v1 未定义它存在哪里 |
| 3 | 修正"没有面板 = 没有持久事实" → "没有 ProductTask 面板 = 没有 ProductTask / Workspace / Promotion 变更" | 普通聊天本就写 Session Event，v1 表述不准确 |
| 4 | 新增 `assembly_digest`、`requirement_digest`、`source_base_revision`；Reader 交叉验证 | profile 不变 ≠ 装配不变；`main` 是可移动引用 |
| 5 | Profile 七维预算全部显式；`model_input_limits` | `BudgetLimits` 源码明言不得有隐藏默认值 |
| 6 | **Reviewer 移到 coder 之前**，coder fresh-read 两份 report；跨 Agent 注入有界并留截断证据 | v1 的 reviewer 在 coder 之后无人消费其意见，是昂贵旁观者 |
| 7 | Router 改为**真实 Agent + Session + Budget Account** | `_require_agent_session`：普通 Session 不进 Budget Ledger，v1 的说法是错的 |
| 8 | 固定执行顺序：Router 在 `task-opened` **之后** | v1 让 preflight 既"无持久事实"又显示 Router 成本，自相矛盾且无法归属 |
| 9 | 硬中断只能 `/inspect` 或 `/abandon`（标注资源未证明释放），不得 `cancelled` | E 无公开 cancel API，也无法证明清理干净 |
| 10 | Benchmark 决定在 F0 冻结：重构 `traceh eval`、替换旧 schema、不留适配层、走真实 ProductTask 表面 | F0 是冻结阶段，不能把选择留给实现者 |
| 11 | 阶段拆成 F0–F5 | v1 的 F1 过大（Ledger + 装配 + Chat + Router + 拓扑 + 面板） |
