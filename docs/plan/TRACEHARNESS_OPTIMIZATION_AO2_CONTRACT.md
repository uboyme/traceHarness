# AO-2：真实提案与独立语义审阅执行合同

本合同冻结 AO-2 的实现和验收范围。程序检查硬约束，独立模型按固定 rubric 评价语义，用户决定采用；模型评分不是人工批准。

## 1. 本阶段主线

1. 用户显式提供开发观察、允许编辑的文本、模型连接和调用预算。
2. 原 Plugin / Generation / Lease 装配可信策略插件。插件借用宿主 OptimizationAnalysis，只接收 AO-0 的受限请求。
3. 宿主使用原 AgentRuntime、Session、BudgetLedger 和 Provider 执行一次无工具分析，保存实际请求、响应及 usage。没有绕过 Runtime 的 SDK 调用。
4. 严格解析模型提案，原 admission 校验身份、文本范围、旧值摘要和去重；交给 AO-1 的原双臂评估入口。
5. 原评估证据导出后，独立无工具 Session 按冻结 rubric 作语义审阅；评分产物明确标为 model，仍经过原 assess / comparison 的硬约束检查。
6. 冻结候选后，在未交给提案模型的案例组上作一次验证。失败、无候选、证据不足或无收益均保留，结束实验。

AO-2 每个入口只生成一份候选，不自动连续调整或采用。AO-1 的人工队列仍可用；共用原评估和比较主线，不增加第二套评分器、事实源或执行循环。

## 2. 身份和权限

- 提案模型看不到 gold、rubric、评分实现、holdout、密钥或真实用户 Session。开发观察由调用方明确选择，原文长度受 AO-0 合同限制。
- 裁判只接收固定 rubric、题目、答案、预期和原请求中实际到达的证据/检索轨迹；不暴露 baseline/candidate 标签或提案理由。
- 新模型审阅必须保存 origin、模型条件、原 Session 定位与摘要；不得伪装成人类 reviewer。旧审阅协议若改变，明确拒绝旧格式，不静默猜测。
- 比较只提供开发候选建议；Promotion、安装、Git 和当前代码修改不属于运行入口的权限。

## 3. 预算、失败和收敛

- 分析和裁判分别有显式输入 token 策略、输出上限、总 token 额度、墙钟期限；一次调用只有一个 Step，不重试、不开放工具。
- 每次调用创建独立 Agent/Session 并通过原预算账本授权；未知 usage 记 unknown 并停止自动资格判断，不记零。
- 报告分列试验、提案、裁判成本；不能用控制模型的额外成本美化试验 token 降幅。
- 取消必须等到 Provider、Runtime 和 SQLite 关闭；重复取消不得提前返回。失败记录保留实际调用，原错误与 cleanup 错误同时保留。
- 一次实验的调用数、完整双臂 trial 数和时间必须在调度前可容纳；未满足时不发起请求。

## 4. 验证边界

定向测试包括正确提案、越界提案、无候选、假语义通过、错绑原证据、未知 usage、模型失败、重复取消及 cleanup。关键保护做反向验证。真实测试冻结小规模开发集与新 holdout，直连现有授权 Provider；不重跑 72 题，不跑全量、L2–L4、Wheel，不提交或发版。

报告区分硬门禁、模型语义判断、人工采用决定，公布实际调用与 token、保留失败分母。不把小样本结果称作总体 benchmark 提升。
