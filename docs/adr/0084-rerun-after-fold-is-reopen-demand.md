# ADR-0084：折叠后重跑同一调用计为重开需求

状态：**已决定**。日期：2026-09-24。修订 12.2“由该证据定位并修复的两个折叠根因”中的有界读回保护；
`surface/replace` 的形状、`FoldBoundary` 字段、字节预算、占位符和排序规则不变。

## 背景

收口计划实验 B（[记录 087](../deal/087-task-type-context-evolution.md) §3）在 48k 窗口下对照开/关上下文治理，
同一题各 2 次：

- 关治理 2/2 通过；开治理 0/2，两次都在修复阶段因 Turn 期限被取消。
- 开治理时主方读回 0 次，折叠后重跑同一调用 11 次和 4 次。

逐事件核对：

- 占位符写明“read to reopen, do not rerun”并给出可执行的读回参数，但模型重跑了原 `read_file`。
- 这些重跑结果按原规则是普通候选，约两步后再次被折叠，于是再重跑，时间就耗在这个循环里。
- 既有的“需求优先、容量有界”保护（记录 084 §6）只统计读回工具的调用，所以看不到这种需求。

## 决定

在同一字节预算 `kept_recent_readback_utf8_bytes` 内，受保护的“重开证据”扩为两类：

1. 读回页（原规则不变）；
2. 某次调用的最新结果，条件是该调用是“折叠后重跑”：同一工具、规范化后参数完全相同的调用，
   发起时同一调用已有更早的结果被 tool-fold 折叠。其需求计数就是当时已被折叠的同调用结果数。

两类统一按“需求优先、新近度作平级次序”排序，装不下的跳过。

- 同一调用只保护最新那份；更早的副本仍可折叠。
- 结果仍可见时的重复调用不算需求：改完代码后再跑一次测试是新工作，不是找回丢失的证据。

这一判定只读 Session 事件前缀里的 `tool/call`、`tool/result` 与 tool-fold `surface/replace`。规划器与验证器共用同一个函数，
重放时得到同一集合。它不读取 Effect 流里的 `effect_kind`，也不硬编码任何工具名。

## 后果

- 预算为 0 时行为与原来完全一致。
- 协议字段不变。旧 Session 如果含有“按新规则会受保护”的历史折叠，在新代码下会被验证器以
  `tool-fold-source-mismatch` 明确拒绝，不会被静默接受或改写。按 pre-1.0 约定，这类数据应使用新数据目录；
  已冻结的评测证据按各臂保存的冻结源码解释。与记录 084 §6 修改排序时的处理一致。
- 读回页与重跑结果共用同一预算。频繁重跑会占用本来留给读回页的容量；这是有界的，并按需求排序。

## 被否决的方案

- **重跑时由宿主直接返回已折叠的原结果**：文件可能已被修改，重跑的语义是“读当前状态”，
  返回历史字节会让模型看到过期内容。
- **按 `effect_kind` 只保护只读工具**：Session 流不记录该字段；跨流读取会让验证器依赖第二条流。
- **任何重复调用都算需求**：会把结果仍可见时的正常重复（例如重跑测试）钉在上下文里，
  反向测试证明这一区分必要。
- **加大 `fold_protect_recent_groups`**：只推迟颠簸，不识别需求；还会让所有近期结果一起变贵。
