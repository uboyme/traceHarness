## 2. 要交付什么

一主、多个直接助手、一次结构化分工，每个助手拥有独立身份、预算、工作区与交接证据。主方自主决定是否立即等待、做哪些独立工作、先收谁的结果及补丁整合顺序。工程分阶段不等于给模型规定“第几步必须做什么”。

第一版边界：

1. 保留 single；multi 允许一个或多个助手，不强制多开、不强制同时推进。
2. 原 investigator / patch_author 是权限模板，可以分别实例化多次；同一计划支持只读、可写混合，不能因开启 patch_author 就把全部助手变成可写。
3. 不做递归团队、子方再派发、追加/替换助手、动态 DAG、消息广播、队列调度、自动扩容或自动冲突合并。
4. 第一版一次提交完整助手集合；N 由主方在宿主上限内选择。先用 2 个助手证明多子并发，再用 3 个助手的离线独立案例证明没有写死数量 2。
5. 当前默认配置保持只允许一个助手；显式提高宿主上限后才允许多助手。预算允许的数量是上限，不是要求用满。

## 3. 统一合同建议

### 分工与身份

把单一 child 改为非空 children 列表，每项具有计划内唯一、非空的 assignment_id、明确 role，以及原 goal/scope/exclusions/deliverable/briefing。main_work 保留，handoff 保留两种返回语义。此为拟定字段，阶段 A 根据当前 owner 确认唯一最终 schema，再写新 ADR；不长期同时维护 child/children 两条逻辑。

assignment_id 只是计划内关联键，不授予权限；宿主从真实 owner、原调用身份和 assignment_id 派生不同 child/session/message/reservation 身份。所有后续操作必须绑定真实 agent_id + message_id，以及所属计划/任务；不能用列表下标、角色名或模型自报的 Artifact 代替身份。

N=1 保留两种使用行为，但不承诺旧 JSON 字段永久兼容。检查 schema 变化影响的 Profile、Session/Context、工作信封及派生协议，按实际合同选择版本升级和明确拒绝；不要盲目升级所有协议，也不能在同版本下静默猜测旧结构。旧实验原库保持，必要时使用新数据目录和冻结旧代码读取。

### 派发与资源

先验证完整计划的字段、角色授权、唯一性、数量及可计算的整批资源需求，再经原 Budget/Workspace/Supervisor 派发。语法或未授权角色错误必须零派发。可复用 coder.budget.max_children 表达本阶段唯一一批直接助手的数量上限；先核对根→主→子的实际层级与单调约束，不能把根账号的直接子数误算成业务助手数。max_processes 不是模型并发数。

逐项建立预算预留时仍使用原串行化/CAS 准入，先前检查不代替最终原子准入。全部助手的初始 token、步数、工具和时间预留加上主方已在途预留必须可容纳，不能把同一份剩余额度复制 N 份。若原模板额度无法整体容纳，明确返回可纠正的资源不足，不擅自缩小任务或增预算。

创建/发送可以按短暂顺序执行，但不能创建一个后先等其任务结束才创建下一个。多个 create/send 本身不要求并行；真正要重叠的是助手工作。

若第 k 个助手创建/发送失败，收敛本批已启动的助手，释放未使用预留并保留已产生事实，再返回明确失败。不能宣称跨 owner 的“全有或全无事务”，不能自动重派整批。成功派发返回全部精确身份后，后续生命周期归原 Product owner 树。

本阶段一批 N 必须能同时获准，不引入后台排队。若未来要支持“总共 10 个、最多 2 个在跑”，那是另一份队列调度合同。

### 等待、收集与完成

`dispatch_and_continue` 在整批消息接受后返回，主方继续；`await_report` 先派发整批，再等待全部，主方阻塞但助手之间仍可并发。N=1 的默认等待效果保持。等待共享一个截止时间，不能每个助手重新获得完整总时限。

主方可以按 exact agent/message 收集任意一个，不因 A 尚未完成而阻止收集已完成的 B。混合角色时应开放两类已授权收集工具；对错误角色或他人消息明确拒绝。pending 只表示未完成，不是成功报告或失败。取消一次收集只取消等待；取消主任务才停止整个所属树。

状态导航从原 Directory/Inbox/Session/Effect 派生并进入既有冻结上下文，不建内存“已完成表”替代事实。展示每个 assignment 的身份、角色、状态和是否已收集，帮助主方减少盲目轮询。终局状态和收集状态分开，完成不等于主方已经读到结果。

最终门禁对集合检查：所有已接受 assignment 都有同身份、已结算、成功收集的完成报告；任一 pending、失败、遗漏或身份替换都不能通过。一份报告不得抵充另一个助手。第一版全部助手都是必需交接，不引入自动忽略失败或主方静默接管；如需可选助手，另订明确放弃合同。

助手运行失败后可以让主方保留独立工作，但不能当整批成功；主方结束/失败或用户取消前必须收敛所有助手，保留已完成的报告/Artifact，不删除成功兄弟的事实。取消、重复取消、部分 cleanup 失败必须覆盖整树，不能首个异常让其余助手泄漏或遮蔽原错误。

### 多份 Patch

每个可写助手独立 Capture，独立完整读取，独立 integrate_child_patch；主工作区内的整合仍串行，经原 Effect 与前像核对。第一版要求可写助手最终补丁的改动路径互不重叠；重复路径给出明确冲突，不自动选后到者，不做文本 rebase。scope 的自然语言描述不是新的文件权限，不可宣称已提供路径级授权。

完成证据从“唯一 Artifact”变为按 assignment/agent/message/artifact 绑定的一组交接与 applied 回执；同一助手重复收集去重，不同助手不能合并成一项。不要要求所有助手补丁字节相同，也不要因 B 改了无关文件，就误判 A 的有效整合失效。

先核对原 `_target_plan` 的摘要和前后像语义：多次整合必须保留可验证的顺序和各自 touched-path 绑定，既拒绝真正前像漂移，也容纳无关路径变化。不得仅把旧函数的第一个结果改成列表就宣称完成。主方后续编辑是否使原回执失效，保持原已承诺规则，在 ADR 明确并测试；不能为让多补丁通过而去掉前像、身份或应用结果校验。

最后仍捕获主方最终 Artifact，对完整候选运行原固定 Verifier、Review 和人工 Approval/Promotion。多份子补丁都 applied 不等于完整任务通过。

## 5. 最低验收矩阵

- single 正常；N=1 默认等待、显式并发都通过，旧人工门禁不变。
- 两个助手都进入真实运行且未结束时，主方完成自己的真实工具操作；使用 Event/Gate 确定性证明，不靠 sleep、名称或 running 标签。
- 另一个 N=3 案例，以及两只读、两可写、只读+可写混合；数量不是写死的 2，角色不是助手身份。
- A 慢、B 快：可先收 B；重复收 B 不重复 Capture、不抵充 A；错误 agent/message/来源/任务拒绝。
- N 超上限、重复 assignment、未授权 role 在派发前拒绝；整体额度不足及准入时剩余额度变化不超发、不泄漏。
- 第二个创建/发送失败时，第一个停止且第三个未启动；主任务取消同时停止在途主子操作；重复取消、单个清理失败仍尝试收敛其他助手；收集取消不误杀子方。
- 两个助手同文件冲突明确失败；不同文件逐个整合成功；伪造、遗漏、替换一份报告/Artifact/applied 回执时不能最终交付。
- 助手全部完成但未全部收集时拒绝交付；固定检查失败仍不进入人工批准；批准前目标 ref 不变。
- TUI 同角色多实例、窄终端、总/单 Agent 用量、打开时快照与运行中刷新语义正确；不把重叠时长或累计时间直接解释为提速。
- 原 Session 请求可重放；账本复制核验不改原库；所有账户/预留、owned tasks、Workspace、沙箱均终结或按原合同隔离，不能只断言 live 数量为零。

只跑定向与直接相邻回归、compileall、collect-only、修改范围 Ruff、文档和架构/协议检查。不跑全量、L2–L4、Wheel、安装、镜像拉取或递归联网门禁。关键反向验证选择真实交付/身份/取消合同，不能为了凑失败破坏夹具启动。

真实验收建议仅一题一次、一主两可写助手加主方独立工作，先用功能预检证明空实现失败、参考实现通过。建议整树最多 60 次 Provider 调用、900 秒、单次连接 60 秒、零重试；这是待授权的试验上限，不是生产默认或现在的调用许可。Token 必须另行冻结任务总额、主方子树、每个助手初始/累计额度与主方保留额，不得直接乘 N 后无限扩大。测试题可明确要求验证两个助手，但不得把这种强制用法宣传为模型自然择优或加速收益。
