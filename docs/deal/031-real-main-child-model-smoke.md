# 031：真实主 Agent 与只读助手小规模验收

## 要回答的问题

本轮只核对三件事：真实主模型是否会按任务难度选择委派；真实助手能否沿原 Product/Supervisor/Session 主线执行；主方能否收集报告并完成任务。它不比较单/多 Agent 成绩，不运行语义裁判，也不改变默认 `single`。

运行前冻结源码、测试材料、现有 Docker 沙箱和调用上限；模型为现有授权连接的 `qwen-plus`，直连、每个请求只尝试一次。结构验证先在无网络 Docker 中做反向检查：原始材料失败，合格参考产物通过。

## 真实结果

自然行为共三个单次场景。简单版本读取题用主模型 5 次完成，未委派，20,753 exact tokens。两个九文件复杂评审题各使用主模型 16 次，分别完成逐文件读取与不同关键词搜索，但都没有调用 `delegate_investigation`，也没有额度申请或决定；下一次请求被本地调用上限拒绝。调用轨迹持续推进，没有相同预算决定或同参数工具循环。

随后做明确委派连通性检查。十八文件题实际调用主模型 4 次、助手 8 次，成功委派并成功收集一次报告；任务在后续主方调用前达到 12 次本地上限。为避免提高上限重跑大题，又使用仅含 `src/traceh/version.py` 的最小题：主模型 5 次、助手 3 次，助手完成 `list_files → read_file → 报告`，主方完成 `list_files → delegate → collect → 写文件 → 回读`。生成的 `answer.json` 经冻结 Docker 验证器离线返回 0；但回读后的最终模型结束消息需要第 9 次调用，8 次本地上限先拒绝，因此原 Product trial 仍如实为失败。

两类明确题共同证明了真实主模型、真实助手、owned child、原消息交接和 collect 链路可以工作；没有一条同时取得“真实双模型 + Product completed”，不能宣称完整双模型任务验收通过。自然复杂题没有委派，也不能宣称模型已形成自主协作或额度申请策略。

## 用量与审计

所有场景合计 **57 次真实 Provider 调用**：主模型 46 次、助手 11 次，成功调用的服务端精确用量为输入 504,957、输出 4,222，共 **509,179 tokens**。四次后继模型 attempt 在进入 Provider 前由本地上限拒绝，没有外部调用、没有 usage；运行级 Token 因失败 attempt 按合同保持 unknown，不能用已知和冒充完整账单。外部 Provider 失败为 0。

离线重开 17 个 Session，复核 71 份 Request Snapshot；请求重建和核心不变量错误均为 0。全部场景预算收敛、Workspace `live=0`。第一次复用通用重放助手时，关闭只读 SQLite 连接清除了空 WAL/SHM 副文件，文件集合断言因此失败；持久数据库未变。随后排除临时副文件，对持久文件做前后摘要并重新完成全部重放。

第一次三场景驱动把任意 `provider_failure_categories` 都标成连接失败，错误地把本地调用上限写成 `provider-connectivity-failure`。冻结原结果未改写；续跑合同和本记录按事实将其归为 local-call-cap。该问题属于研究驱动分类，不是 Provider 网络故障。

精简机器证据见[真实主子验收摘要](../validation-data/dynamic-collaboration/real-main-child/summary.json)。完整本地证据没有保存 profile、API Key 或代理值。
