# 084：折叠机制的根因修复与真实复测

日期：2026-09-21。承接[日志诊断 082](082-c4c-context-and-late-stop-diagnosis.md) 与
[开源对照 083](083-open-source-agent-context-research.md)。
范围：实施 082 §5 的四项，各自做会失败的反向验证，再沿原 Runner 跑同一真实任务；
每轮真实结果定位下一层根因，据此又补了 §6、§7 两项。**未实施轮内摘要检查点**
（083 §5）：它是唯一需要额外模型调用的一项，有独立的费用与失败模式，
应作为单独的协议阶段设计；按 082 的拆解算术它目前也不是约束项。

## 1. 为什么是这三项

082 把 run3 被拒的 65,759 拆开后，机制自身开销占 72.6%（占位符 19,766 + 永久豁免的读回 27,970）。
也就是说"必需证据装不下窗口"的说法不成立，先修机制比扩窗口更有意义。
083 的四个开源实现给了两条可借鉴的形状（分层老化、按容量保护）和两条不能照搬的（允许重跑原工具、
几十 k 的保留阈值）。

## 2. 及时停止：判定从"最终交付"移到"每个 Step"

**缺陷**：`CollaborationContinuation.decide` 只在 `Finish("completed")` 时调
`_require_collected_report`，工具步一律放行。因此它是**最终交付检查**，不是及时停止。
实测代价：主方 04:55:17 拿到 `status=failed`，此后又 17 次调用、562,727 token、18.52 分钟才被拒。

**修复**：新增 `_stop_on_undeliverable_report()`，每个 Step 后核验本 Step 的 collect 结果：

- 身份必须匹配本 Turn 已派发的 `(agent_id, message_id)`，否则忽略——杂散载荷不能停掉运行；
- `status == "pending"` 不是终态，交给既有等待与墙钟边界；
- 终态非 completed → `CollaborationChildIncomplete("collaboration-child-terminal-failure")`；
- completed 但 `statement` 空白 → `CollaborationChildDeliveryEmpty`。

必须区分的一点：collect **工具结果**的 `status=succeeded` 只表示取报告成功，
报告**内部**的 `status` 才是助手终态。把两者混为一谈正是旧代码放行的原因。

**测试的修正同样重要。** 旧用例只断言抛出异常，时机写在注释里——拿注释当证据，
属于 AGENTS §7 点名的空验证。新用例让脚本主方在拿到终态报告后**故意还想继续干活**，
断言 `provider.calls_after_terminal == 0`。反向验证：移除该检查后，那个主方一路跑到
`max_steps_exceeded` 才停，正是"停得太晚"的形状。

## 3. 紧凑占位符：232 → 102 token

占位符永远不能再被折叠，所以它的每个字段都是永久成本。run3 的 67 条占了 19,766 token，
约请求的 30%。拆开看，三分之一是同一段散文抄了 67 遍，还有一份 effect_id + digest 的重复
（`output_ref` 里一份、`read_action` 里又一份）——**后者是我上一轮自己加进去的**。

改后的形状：

```json
{"folded":"historical output; read to reopen, do not rerun",
 "status":"succeeded","chars":2760,
 "read":{"tool":"read_tool_output","arguments":{"effect_id":"...","digest":"..."}}}
```

去掉的：71 token 散文（压成自足短标记，完整说明是提示词材料，说一次）、
整个 `output_ref` 对象（身份只留 `read` 里一份）、`format` / `disclosure` /
`content_utf8_bytes` / `data_chars`（宿主协议元数据，审计从事件里读）。

用真实摘要实测：**232 → 102 token**。按 run3 的 67 次折叠推算 19,766 → 6,834，
那次被拒的 65,759 会变成约 52,827，**在 61,184 之下**。

**保留自足性是刻意的**：说明可以精简，但占位符不依赖系统提示存在才可读——
换组合或事后重放时它应当简略，不应当变成天书。

## 4. 有界读回保留：撤销永久豁免，折回原页

上一轮为了堵"取回来又被折走"的跑步机，我把读回结果**永久**排除出候选。
082 指出这只是把失败搬了个地方：28 条永久保留占 42.5%。这是过度纠正。

**为什么原来的理由不成立。** 我当时说"折读回结果会让一层引用变两层"。
真正的机制是：占位符若指向读回工具**自己的**输出，重开它会拿到"包着上一层页信封的页信封"，
每折一轮多套一层。而把占位符指回**原始页**——地址就在该次读回调用自身的参数里——
就是模型已经发过的同一个调用，**幂等、一层、不套壳**。理由随之消解，豁免不再必要。

**保护改为按容量。** `FoldBoundary` 增加 `kept_recent_readback_utf8_bytes`：
从最新往回累计重开页的 UTF-8 字节，装不下的那一条起停止保护，更老的正常参与候选。

两个刻意选择：

- **字节而非 token**：本协议模块不应引入 tokenizer，且 validator 必须原样重算。
- **容量参数写进 fold 事件**：这是我们和那四个开源实现的关键差别——它们可以用运行期计数器
  决定保留谁，因为不承诺历史请求可重放；我们承诺（68 份快照逐字节重建是本轮验收项），
  所以保留决策必须是**事件前缀的纯函数**，重放不能去查今天的配置。

实现中发现一个真实缺陷：`surface_tool_links.calls` 映射到的是 **assistant 消息**，
不是 `tool/call` 事件，因此拿不到参数。新增 `fold_source_call()` 直接定位 `tool/call`，
planner 与 validator 共用同一解析，避免两边对"折叠允许说什么"产生分歧。

**反向验证**：去掉容量保护 → 受保护的重开页被折走，用例失败；
把地址改回读回自身输出 → 原页断言失败。两条都会失败，不是空验证。

**已知代价**：容量给得过小，重开证据会较快老化；给得过大，它仍会挤占窗口。
这是显式配置，没有通用默认值。

## 5. 有限收尾：耗尽前撤掉工具

**缺陷**：助手跑满 25 分钟墙钟被取消，交付为零，此前 47 次调用全部作废；
它自己的消息显示"核心证据已经拿到"之后仍在继续搜集。宿主从来没有告诉它该停。

**修复**：新增 [`supervision/investigation_wrap_up.py`](../../src/traceh/supervision/investigation_wrap_up.py)。
`WrapUpReserve{steps, tool_calls, wall_milliseconds}` 从已授予的额度里预留一段，
到线后 Step 视图**给出空工具列表**，只保留收尾指引。

三个刻意选择：

- **撤工具而不是提示"请停止"**。083 比较后取 OpenClaude 的形状；Gemini 的宽限重试仍走普通
  `executeTurn`，宿主不保证工具已撤。本例中的模型已经证明它不听劝——冻结请求里没有工具可调，
  唯一能做的动作就是把结论写下来。
- **绝对值而非百分比**。大额度的百分之几仍然可能不够写一份报告；只有宿主知道自己的模型要多久。
- **墙钟从事件时间戳推导，不读时钟**。读时钟会让决策不可重放。最新事件最多落后一个 Step，
  低估是预留量的安全方向。

**主方同样接线**，但收尾视图**保留 collect 工具**直到所有报告到齐——否则协作合同会变成
不可满足：既要求每个 assignment 都收到报告，又撤掉取报告的手段。

**实测**：这是整个序列里助手第一次真正交付——`completed`，12,732 字报告。

## 6. 需求加权的读回保留：同一页被重开四次

§4 之后又跑了一轮真实任务，结果同时给出好消息和一条新的根因。

**好消息**：重跑原工具基本治好了。助手 116 次工具调用里，`read_file` 重复只有 **1 次**
（run1 是 22，run3 是 9）。

**新根因**：抖动搬进了 reader。60 次 `read_tool_output` 里 **31 次是完全相同的
`(effect_id, digest)`**，五个页面各被重开 **4 次**；读回占了它全部动作的 52%。

拆开看就是容量抖动：按纯新近度保护，一个页面只要有更新的东西到来就被挤出——包括模型刚刚
花一次调用取回来的页面。它随即被折叠、被重新取回、再被挤出。§4 让每次重开**幂等且只有一层**，
这一点成立；但它没有限制**同一页能循环多少次**。工作集大于容量时，这就是标准的缓存颠簸。

**修复**：同一字节预算内，**按已证实的需求排序，新近度只作平级时的次序**。
模型已经付费重开过的页面，就是它的工作集；容量本来就是为持有工作集而存在的。
读一次再没回头的页面才是该放掉的那个。重开次数同样从事件前缀数出来，保持可重放。

顺带改掉一处：装不下的页面现在**跳过而不是终止扫描**。纯新近度下"第一个装不下就结束"表达的是
"保护一段连续的近期窗口"；改成需求排序后没有连续性可言，一个超大页面不应该把它后面的整个
工作集一起赶走。

**反向验证**：把排序换回纯新近度 → 新用例失败，且失败形状正是根因本身——预算被花在模型
要得最少的那一页上。用例让模型重开 A 两次、B 一次并**以 B 收尾**，所以两种排序必然给出
不同答案，不会两边都过。

**已知代价**：需求是历史计数，不会衰减。一个曾经热门、后来不再需要的页面会多占一会儿容量，
直到更热的页面把它挤走。在有界预算内这只影响先后，不产生无界保留。

## 7. 传输重试：默认额度对长任务是错的

连续两轮真实运行终止于 `provider-tls-eof`。这不是本轮机制问题，但它挡住了测量。

查证据后事实很具体：重试**是**生效的——第 34 步 ordinal 1 失败、ordinal 2 成功。
第 35 步 ordinal 1、2 都失败后就没有第 3 次了，因为 CLI 默认是**三次尝试且总计 30 秒**，
而这个供应商失败一次握手要 10–15 秒。于是"三次"实际上只有两次，一次网络抖动结束了整场
40 分钟的调查。

改动只在试次脚本：显式传 `--model-retry-max-attempts 5 --model-retry-max-elapsed-seconds 180`，
并写入预登记的已披露条件变更。**不改发布默认值**——那个取舍属于宿主逐次决定；
交互式 Session 不该为一次握手等三分钟。这只放宽单次冻结请求的传输恢复，
不重试任务、不重派 Turn、不改任何停止条件。

## 7.1 撤工具拦得住调用，拦不住模型把最后几步花在上面

run12 是第一次**零 Provider 失败**的运行，也第一次证伪了 §5 的设计理由。
收尾触发了，工具撤干净了，拒绝也生效了（`ToolDenied`，"No calls executed"）——
然后助手仍然没交付：

```
第 33 步  收尾视图（零工具）→ 模型发出 6 个 read_tool_output
          → 全部被拒 → 这一步白花 30.4 秒
第 34 步  收尾视图 → 未及回答即撞墙钟取消
```

我在 `investigation_wrap_up.py` 里写的"冻结请求里没有工具可调，唯一能做的动作就是把结论写下来"
**是错的**。模型照样调。而**把它拉回去的正是本记录 §3 做的紧凑占位符**：
历史里每条折叠结果都带着 `"read to reopen"` 和一个现成的 `read` 动作。
那个承诺对其它每一步都成立，对收尾这一步不成立，而没有任何地方说过这件事。

拒绝回执又恰好什么都没说：

```
Not callable in this Step: read_tool_output. Callable here: .
```

空列表渲染成一个孤零零的句号。模型刚被撤掉工具、最需要知道现在该做什么，拿到的是这个。

**两处修改**：

- **零工具的 Step 不再渲染空列表**，改为陈述状态与唯一出路：
  "This Step publishes no tools at all, so no call can succeed here. Answer with text only."
  一个 Step 故意不发布任何工具是正当形态——有限收尾就是这么逼出最终答案的。
- **收尾指引显式作废占位符的承诺**：告诉模型那些 read 动作对其它每一步有效、对这一步无效，
  试一次只会白花仅剩的预算。

执行层本来就是对的。缺的是**说清楚发生了什么**：拦得住调用，拦不住模型把最后两步耗在上面。

## 7.2 重试共用一份预留：失败尝试不再各扣最坏值

run11 死于 `BudgetExhaustedError`，但助手只做了 725,467 token 的真实工作：

| | |
|---|---|
| 助手额度 | 2,000,000 |
| 真实消耗 | 725,467（34 次成功调用） |
| **20 次失败尝试被扣** | **2,000,546**（`usage: None`） |

机制：拿不到响应时 `usage_quality` 记 `unknown`，按**预留最坏值**结算，
每次 83,402（输入估算 + 32,768 输出预留），而那次调用一个 token 都没产生。

**重试本身是对的且必需**：那轮 64 个请求里 7 个遇到失败，**6 个靠重试救回**，
其中 3 个要到第 3、4 次尝试。根因不在重试，在**同一个冻结请求的 N 次有界重试被当作
N 个独立请求各扣一次最坏值**——而宿主自己用 `ModelRetryRequestDriftError` 证明了它们是同一个请求。

**修复**：不可观测的那一笔由**第一次遇到失败的尝试承担一次**，后续 ordinal 结算为 0。
让出的只是"倍数"；保守规则真正要防的（一次请求可能白花一次最坏值而无所得）仍然成立。

**真实主线已确认**（run13 证据）：ordinal ≥2 共 3 次结算，合计 **0** token；
ordinal 1 的 4 次失败合计 414,122。按旧逻辑那 3 次会再扣约 30 万。

**这个缺陷仓库里本来就有标记**：`test_an_uncounted_reservation_leaves_no_budget_for_the_mandated_retry`
的 docstring 写着"修好后请换成对照用例的断言"。本次修的是**倍数**那一半；
该用例针对的是"没有 tokenizer 时单次预留吞掉整个账户"，是另一半，原样保留。

**一个必须记下的自我纠正**：§7 把重试从 3 次放宽到 5 次，在记账修好之前**放大了**这个缺陷——
每次抖动的代价从约 20 万变成约 50 万。run11 的失败是那次改动造成的。
反过来，记账修好之后，"多试几次"才真正只带来可靠性、不带来账单；
run13 据此把时长上限从 180 秒放宽到 600 秒，理由是原来卡紧的成本前提已经消失。

→ run8 1,750,535。

**§6 的效果要看分布而不是总数。** run7 与 run8 的"折叠后重跑"是 33 → 19，
但真正说明问题的是重开的多重度：

| 同一页被重开的次数 | run7 | run8 |
|---|---|---|
| 4 次 | 5 个页面 | **0** |
| 3 次 | 4 个页面 | **0** |
| 2 次 | 3 个页面 | 13 个页面 |
| 1 次 | 其余 | 16 个页面 |

深度循环消失了，上限降到 2。取回两次不是跑步机——第一次重开很可能发生在原页被折叠之前。
同期 `read_file` 的重复是 4 次（run1 为 22）。

几条值得单独说清楚的：

- **上下文问题本身已经解决**。run3 那次越限之后再没有出现过第二次；run4 起峰值全部落在
  61,184 之下。这是机制结果，不是运气——`RequestTokenBudgetExceeded` 在越限时必定抛出。
- **run7 的 33 次重跑不是退步，是换了地方**。`read_file` 重复只剩 1 次，31 次是
  `read_tool_output` 重复；§6 针对的就是这个。
- **run8 确认了 §5 在真实主线上生效**：助手视图出现 `investigation-wrap-up`，预留按墙钟触发。
- **run7 的结局与本轮机制无关**。助手第 35 步连续两次 TLS 握手失败，主方的**每步停止**
  随即生效，当步以 `collaboration-child-terminal-failure` 结束——这正是 §2 想要的形状，
  代价是零额外调用（最后一次 collect 之后模型调用为 0，1.9 秒后记录失败），
  与 run3 那次 562,727 token / 18.52 分钟的迟到失败形成对照。
- **run8/run9/run13 是供应商侧中断，不是结果**。run8 的失败窗口里主方连续 5 次尝试、
  助手 3 次尝试**同时**失败；run9 24 次调用失败 14 次（tls_eof 8、disconnected 5、timeout 1），
  连分工计划都没走完；run13 主方一个请求连续 `tls_eof → disconnected → tls_eof`。
  当供应商确实处于中断时曾暂停投入：对一个正在宕机的服务反复下四十分钟的注不是诊断，
  应先用一次廉价探测确认它恢复了没有。
- **固定 Verifier 仍未跑到**，所以"补丁是否正确"在整个序列里一次也没有被判定过。
  本轮的全部结论都关于上下文机制与交付纪律，不关于任务质量。

### 8.1 每轮死在不同的 owner 上

这是本序列最该记住的事实：run4 起上下文越限再未出现，此后**九轮没有一次死于上下文**。

| 运行 | 死因 | owner |
|---|---|---|
| run4 / run5 | 顶满墙钟被取消 | 监督（收尾缺失、只接了一半） |
| run6–9、run13 | 传输中断 | Provider / 重试策略 |
| run10 | 畸形采样被判永久失败 | 失败分类 |
| run11 | 失败尝试重复扣额度 | 预算记账 |
| run12 | 收尾被占位符拉走 | 提示与拒绝回执 |

一条四十分钟、两个角色、约百次调用的长链，每修好一环才露出下一环，
而**一次观测只能暴露一个缺陷**——前一个致命故障会掩盖它后面的全部。
这不是同一个缺陷反复出现；这些缺陷分属六个不同 owner，且都只在真实长任务里才暴露得出来
（要么需要真实模型的策略反应，要么需要几十次调用的累积，要么需要一个真会抖的网络）。
其中两项还是本记录作者自己上一轮的过度纠正造成的（永久豁免、在记账修好前放宽重试）。

助手侧"为什么永远跑到被打断"的单独诊断与三项提案见
[记录 085](085-multi-agent-convergence-diagnosis.md)。

由此得到一条方法论结论：**上下文机制的验收不应当以端到端任务成功为因变量。**
它已经有离线对照、每请求指标和逐项反向验证；把"整题做对"绑给它，是让它为一条
自己管不着的长链负责。要取得固定 Verifier 的裁决，应另走一条更便宜的路径
（例如 single 模式跑同题，去掉助手那一整条失败链），而不是拿四十分钟的双角色任务做调试载具。

## 10. 待决策：畸形采样被归为永久失败

`provider-tool-arguments-*` 目前属 `protocol` 类，而该类被定义为永久、不可重试。
但这一类混了两种性质不同的东西：**供应商的响应信封坏了**（缺 `choices`、类型不对，重试确实没用），
和**模型自己采样出来的内容坏了**（重开一次采样大概率就好）。
把后者称作"永久"，等于断言一个非确定性模型会永远吐出同一段畸形 JSON。

支持这个读法的是既有代码：`_parse_tool_arguments` 已经有一条
`_normalize_triple_quoted_arguments` 修复路径，专门救某个已知的模型怪癖——
架构已经承认"模型写的参数可能坏且可救"，只是没把这件事反映到重试分类上。

频率：全序列 543 次调用中出现 1 次（run10），直接终止了整轮。

**未实施。** `failure_category` 落盘在 `model/attempt-end` 中，改它就是改持久协议；
且"什么算永久失败"是宿主合同，按 AGENTS §8.1 应作为独立架构决策提出，
而不是伪装成实现修复。若采纳，建议的最小形状是：把模型采样内容的畸形单独分一类
（只含 `provider-tool-arguments-*`）并只让这一类进入可重试集合，信封类 `protocol` 保持永久；
不加别名、不加兼容层。

**不能声称的**：一次运行不足以声明节省率、质量持平或模式收益，模型非确定性已在前几次运行中
明确表现（同条件 run2 与 run3 轨迹完全不同）。固定 Verifier 从未执行，补丁正确性未知。
