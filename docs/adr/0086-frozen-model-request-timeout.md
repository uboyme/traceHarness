# ADR-0086：评测计划冻结单次模型请求超时

状态：**已决定**。日期：2026-09-24。修订 12.5 评测运行计划的 `model` 段与冻结条件；
重试策略、臂间停止规则、Provider 失败分类均不变。

## 背景

收口实验（[记录 087](../deal/087-task-type-context-evolution.md)）当天出现 7 次 `provider-timeout`，
一度被判断为“供应商侧请求挂住”。核对 1,830 次成功调用的原事件后，这个判断被推翻：

- 耗时与输出 token 严格成正比：每 1,000 个输出 token 约 17–18 秒，全天各小时一致，夜间并未变慢。
- 最长的成功调用输出 4,290 个 token，用时 75 秒；75–120 秒之间没有一次成功。
- 输出上限是 8,192 个 token，按上述速度约需 148 秒，而单次请求超时为 120 秒。
  模型一旦推理较长、输出超过约 6,600 个 token，就必然在生成途中被本地超时截断。
- 超时集中在夜间，是因为那段时间运行的恰好是更难的任务（A4/A5 的 Multi、pyvista 与 marshmallow 的验证）。
- 本机排查排除了代理与网络：域名解析为真实地址，路由走物理网卡，Clash 未开 TUN，
  超时前后没有 Wi-Fi 断连或睡眠事件。

更深一层的问题：这 120 秒来自 CLI 默认值或 `TRACEH_MODEL_TIMEOUT_SECONDS`，
**不在运行计划里，也不在冻结条件里**。决定一次长回答能否送达的值，是评测 worker 继承下来的隐藏默认值。

## 决定

- 运行计划的 `model` 段新增必填的 `timeout_seconds`，必须是有限正数，并与 `retry_policy` 同样校验。
  缺失或非法以 `evaluation-manifest-invalid` 拒绝，不回退到环境变量或默认值。
- 计划模式下由计划设置 `model_timeout_seconds`；命令行 `--model-timeout-seconds` 与计划同时给出时，
  以 `evaluation-run-plan-conflict` 拒绝。计划值在环境默认值之前写入，环境变量无法覆盖它。
- `EvaluationRunner` 校验 Provider 实际使用的请求超时与计划一致，不一致按 `evaluation-run-plan-conflict`
  拒绝。离线的 `scripted` Provider 没有网络等待，不参与这项比较。
- `frozen.json` 的 `model.request_timeout_seconds` 记录 Provider 实际使用的值（`scripted` 为 `null`）。
- 本项目的实验工具与 TUI 选题生成的计划取 300 秒，约为 8,192 token 满额输出所需时间的 2 倍。
  历史 live 工具写入它们当年实际生效的值（120/90/60），行为不变。

## 后果

- 旧计划缺少该字段，会被明确拒绝，需要重新生成。按 pre-1.0 约定不兼容、不猜测；
  已完成运行的证据按各自冻结源码解释。
- 超时仍按原失败分类记为 `provider-timeout`，未知用量仍如实记为未知。
- 一个既有的“环境变量决定超时”的 CLI 行为保持不变，只适用于非计划模式。

## 被否决的方案

- **对超时自动重试**：根因是生成本身比超时长，重试会把同样长的生成再跑一遍后再次超时，只会多花钱。
- **放宽臂间停止规则**：只是把问题藏起来，不解决截断。
- **只在环境变量里把超时调大**：值仍不进冻结条件，结果不可复现。
- **按模型速度推算超时**：需要内置模型名与速度，属于隐藏默认值；超时由计划作者显式给出。
