# AO-2：策略提案与独立模型审阅

日期：2026-09-11。阶段实现与限定验证完成，**保留基线，没有采用候选，也没有发布**。

## 1. 做成了什么

现在可以让模型根据明确给定的失败观察，提出一份受限文字修改；程序检查修改范围，原评估器分别运行原版和候选，再由独立模型会话判断语义，原比较器汇总。最终是否采用仍由用户决定。

例如这次提案只修改 Skill 搜索工具的说明：“目录读取被拒绝后，不重复请求同一层级；实际发起新的搜索，再照返回的 read_action 读取。”它没有修改搜索算法、权限、评分器或运行循环，也没有把任何题目答案写入提示。

框架确实执行了这份候选：一道英文问题原先找到手册却停在目录，候选读取到了正文中的签到卡代码。但一次答对不能证明整体更好，负例判断和裁判自身都还存在不确定性，因此没有采用。

## 2. 接在哪一层

- `evolution/strategy.py`：显式装配可信 TextStrategyPlugin，复用原 provide/require、Scope、Generation Lease 和 AO-0 准入；只提出一份候选，交原 AO-1。
- `evaluation/model_service.py`：分析与裁判共用原 AgentRegistrar、BudgetLedger、Runtime、Provider、Session。每次独立身份、一个无工具 Step、有输出/token/期限，无重试。
- `evaluation/model_evidence.py`：从原 SQLite 重建身份、预算、请求和响应，核对派生收据。
- `evaluation/model_review.py` 与 `model_review_protocol.py`：把原成功请求中实际到达的证据、搜索范围和冻结 rubric 交独立裁判；仍由原 review/assess/comparison 决定硬门禁与比较结果。

提案模型看开发观察与获准编辑的原文本；不看 gold、rubric、裁判代码或本轮未见场景。裁判不看原版/候选标签、提案理由和成本。相同远端模型用不同 Session，不代表统计独立或没有共同偏差。

judgment 当前格式为 2，明确 `origin.kind=human/model`。模型评分必须关联原调用输入、输出与证据摘要；手改模型分数会被拒绝。旧格式明确拒绝，旧运行可以重新导出当前审阅模板，不自动改写历史。

## 3. 真实实验结果

使用已有配置加载器连接 `openai-compatible/qwen-plus`，父子进程均直连，无代理、无隐藏重试。四道开发题和五个新场景在分析前冻结；新场景没有传给提案模型。全部试验仍用原 evaluator、同模型/预算与隔离双进程。

| 范围 | 原版 | 候选 | 解释 |
|---|---:|---:|---|
| 开发集 | 3/4 | 3/4 | 模型评分显示一题改善、一题退步；有裁判不一致，见下文 |
| 本轮未见的五个场景 | 5/5 | 5/5 | 相同候选的一次诊断验证，没有质量净增 |

冻结门槛是至少净增一题、Token 不超过原版 1.15 倍、工具调用增量不超过 2。开发集未达到质量净增门槛；新场景也无净增。比较器可能因成本下降标记 `improved`，这不等于晋级，更不等于允许采用。

**裁判限制必须保留：** 开发负例中，两臂都从目录/元数据的无命中推断“手册没有规定”。模型裁判判原版通过、候选失败，原文复核认为这一标准不一致；扫描全部可检索元数据不等于阅读了所有正文。上述分数是保留的原始模型评分，没有手工改分，不能据此断言候选真实净收益或真实退步。需校准的首先是裁判，而不是围绕这道题硬编码运行策略。

费用包含失败尝试，不能只报跑题节省：

| 用途 | 实际请求 | 实际 tokens |
|---|---:|---:|
| 第一份提案：字段类型不符合合同，被拒绝 | 1 | 5,950 |
| 第二份提案：通过准入 | 1 | 5,926 |
| 原版与候选的开发及新场景试验（含历史准备） | 44 | 212,566 |
| 独立语义裁判 | 17 | 103,521 |
| 合计 | **63** | **327,963** |

开发试验 tokens 56,195 → 46,893，工具调用 7 → 5；新场景 55,694 → 53,784，工具调用均为 4。它们只是试验成本；额外分析和裁判花费单列，不能美化为整体节省。所有实际调用 usage 为 exact，模型连接失败为 0。

## 4. 验证中发现并处理的问题

1. 首份真实提案把 `expected_tradeoffs` 返回成数组，原合同拒绝。补清楚通用字段类型说明后，新建实验重新提案；没有转换旧输出或放宽准入，失败费用保留。
2. 单次控制任务使用原 continuation 接缝明确完成，避免把正常的一次回答记成步数耗尽。
3. 重复取消曾可能打断 Provider 收尾。现在只通知同一工作任务取消一次，等待它、Runtime、Budget 和 SQLite 收敛；原错误与 cleanup/发布错误同时保留。
4. 裁判结果不确定、协议无效或 usage 不确定时停止后续裁判，两臂未审部分保留 pending，不继续花费或宣布胜出。
5. 真实驱动的计划字段与候选相对路径曾在调用前被原验证器拒绝，未产生对应 API 调用。修正驱动后只执行尚未启动的冻结验证批次，没有重跑开发题。当前驱动共用一个验证函数，检查原提案身份与开发证据，不是自动恢复入口。

原始执行驱动的确切 bytes 已按冻结 SHA 找回并归档；新场景显式验证入口另存源文件 SHA。已完成实验的 provider_binding 中 `driver_digest` 仍指实验主驱动，当前驱动另外记录 `verification_driver_digest`；没有回写旧证据。

## 5. 验证证据与交付边界

当前 193 项不同的相关检查均有通过结果，含 22 项 AO-2 新测试；首次 193 项相邻回归发现 2 条断言不一致（ProviderFailure 归一化、旧“只有 CLI 消费 evaluation”断言），修正后 39 项复跑全通过。架构保护仅新增已声明的三个 AO owner，其他生产领域仍禁止反向依赖。三项反向保护、compileall、3959 项 collect-only、修改范围 Ruff 与反硬编码扫描通过。

定向集、反向验证、独立重放与原始工件索引见 [AO-2 验证数据](../validation-data/unified-evaluation/ao2/README.md)。63 份原请求、39 个 Session 独立重放通过，原硬不变量通过；重放没有新 Provider 调用。

首轮文件级检查发现变化；在数据库副本上复现了只读 SQLite 连接留下 WAL/SHM、原 Store 关闭清理副文件而数据库 bytes 不变的行为。原调用收据及 trial 证据摘要核验通过，第二轮完整文件检查通过（1,542 个文件）。没有把失败检查当成通过。

本阶段只运行相关测试、相邻 owner 回归和真实小实验；没有全量 pytest、L2–L4、Wheel、安装、提交、推送或发布。真实实验冻结在最终停止/错误合并保护补强之前；最后补强由定向与反向测试验证，不冒充最终源码重新跑过一遍真实 API。

两份上下文同步 1、3、12.7–12.9、13–15、17、19，维护模块、配置、事实源、状态、图和已知边界。没有动态 Workflow、多 Agent 协作、后台连续优化或自动 Promotion。

本阶段证明“一份建议能被受控提出、试验、审阅并拒绝采用”，没有证明“优化模型总能写出更好的提示”或“模型裁判已达到人工可靠性”。
