# 记录 076：大型代码库理解任务的十轮配对对照

2026-09-14。用户授权在记录 074 之后继续测量多助手收益，改用**读多写少**的任务类型。
本记录覆盖第 1–10 轮。**第 1–9 轮全部作废或单臂失败，第 10 轮是唯一一次两臂都完成并通过**，也是本项目第一次拿到「两个都做完了」的成本与质量对照。

## 题目与语料

"读懂这个代码库并写下答案"：交付 `ARCHITECTURE.md`，每条关于代码的断言必须带可解析引用。
语料为本仓库引擎包 Python 加最早 30 份 ADR，**253 文件 / 约 2.7 MB / 6.8 万行**，
**刻意不含任何全项目摘要文档**——否则单体读一个文件即可作答，对照失去意义。

判分**完全机械**，不判文笔：原文件一字未改、只多出交付物、必需章节按序、
**每条反引号路径引用必须真实存在**、锚点引用的符号/行号必须成立、
引用覆盖 ≥25 个文件 / ≥8 个包 / ≥12 条锚点。每轮预检在固定镜像内证明
"缺交付物 exit 1 / 参考交付物 exit 0 / **计数达标但编造一个路径仍然 exit 1**"。

## 宿主侧缺陷（本实验发现并修复，均有独立反向验证）

1. **派发等待时长写死 300 秒**，而单次工具调用上限 60 秒，宿主授权的助手墙钟无法兑现
   （[ADR-0079](../adr/0079-authorized-child-report-wait.md)）。
2. **预算预留取账户全部余额**，且生产无任何路径提供 token 计数器；一次零返回的超时把
   **465 万 token 计给一个空响应**，使声明的重试策略在数学上不可能
   （[ADR-0080](../adr/0080-bounded-token-reservation-and-overage-refusal.md)）。
3. **系统提示 79% 在讲这个 Agent 没有的工具**：实际工具 5 个，提示中详述 `search_history`、
   `read_tool_output`、`request_skill_reference` 等 **10 个不存在的工具**，每次请求白烧约 1,091 token
   （`cl100k_base` 实测；本文早先写的 1,546 是按每 4 字符 1 token 估算，非实测）。
   `source_navigation` 早已按工具条件化，讲解那段却是无条件拼入（正式版 14.3.26）。
4. **拒绝消息不含可纠正信息**：视图检查抢在未知工具检查之前，所以
   `"Unknown tool: …"` 永远不会出现，模型只收到 "Tool batch is outside the frozen Step view"。
   第 6 轮 multi 因此**调用不存在的 `write_file` 五次**（正式版 14.3.26）。
5. **固定检查拒绝合法的行区间锚点** `path.py:148-179`，第 6 轮 single 走完全程后被它判死。

即：主方开始**用搜索定位**而不是挨个读，多助手臂**第一次真的派发了助手、也第一次用了大纲**。

## 第 7 轮的读数与边界（当时口径）

- **可以说**：在这道题上，单体 Agent 能给出通过机械校验的答案；该轮多助手臂未能完成。
- **不能说**：多助手在这类任务上没有收益。它在提交分工的入口被挡住，从未进入执行。
- 前六轮的失败**全部来自宿主侧缺陷或夹具设置**，不是被测机制。
- 每臂一个复本、一个模型（deepseek-v4-flash）、一个端点，属观察而非统计量。
- 第 8–10 轮的结果见下文；**第 10 轮推翻了「多助手在这道题上做不完」这一当时读数**。
- 第 4 轮起语料随工作区重新生成，第 5 轮之后有 2/253 个文件（实现 outline 的那两个）与早期轮次不同。
- 交付物质量数据来自**一份**文档，说明"可以做到"，不说明"稳定做到"。

原始运行目录保留在本机忽略目录，未提交；被中止的第 9 轮首次运行保留在
`comprehension-20260914-r9-killed`。


## 第 8–9 轮：把「机制问题」和「模型能力」分开

第 8 轮补上「类型拒绝附带 schema 已声明的键名」后，旧模型 `deepseek-v4-flash` 仍未过分工门：
它提交一次、错在同一处、**随后放弃**（`collaboration-plan-required-before-completion`），
并自述「none of my available tools」——把「计划阶段没有写工具」误读为「我什么都做不了」。

第 9 轮**只换模型**（同端点、同 key、同语料、同上限）。端点探针证明两者不是别名：
同一句 `hi`，`v4-flash` 计 5 个 prompt token，`v4.1-flash` 计 31 个。结果：

- **`outline` 首次被使用**：两臂合计 332 次；前八轮在完全相同的工具与描述下**零次**。
  工具本身没问题，是旧模型不选它。
- **分工门首次通过**：`failed → failed → succeeded`，被拒两次后**自行纠正**，创建 6 个助手、收 18 份报告。
  这正是第 8 轮那处修正想要的效果，只是需要更强的模型才用得上。
- 两臂仍失败：single 输出截断（16,384 上限），multi **两个助手各自打满 150 万 token 上限**
  触发 `BudgetExhaustedError`，而**主方只用了自身上限的 15%**。

对 `repeated_call_arguments: 119` 的核查排除了「分工没切干净」：106 个重复签名中 **100 个跨不同 session**
（每个助手各自查预算、各自看目录），同一 session 内重复仅 6 个，真正重复读源文件的是个位数。
因此第 10 轮**只抬助手额度与输出上限，不动分工范围**。

## 与记录 074 的对照——同一个机制，相反的结论

| | 记录 074（小模块改码） | 本记录第 10 轮（大库理解） |
|---|---|---|
| 交付物 | 四个各几十行的模块 | 一份 2.2 万字符带引用文档 |
| 助手交回 | **不可变 Patch，主方必须逐字读完再整合** | **压缩过的证据包** |
| multi token | **6.2 倍** | **1.043 倍** |
| multi 墙钟 | **3.2 倍** | **0.93 倍** |
| 判定 | regressed | no_change |

差异来自**整合税**：074 中主方要读 4 份补丁、做 4 次整合、再自测，上下文随之膨胀；
本轮助手交回的是结论而非原文，主方不需要重读，整合税几乎为零。

**这是本项目对「多助手何时划算」给出的第一个有数据支撑的答案**：
取决于助手交回物是否需要主方逐字重读。

## 读数与边界

- **可以说**：在这道题上，多助手与单体**质量持平、成本相当（+4.3% token）、墙钟略快**；
  两份交付物**均零编造引用**。
- **不能说**：多助手普遍划算。一题、每臂一个复本、一个模型、一个端点，是观察不是统计量。
- multi 做了 181% 的工具调用却只多花 4.3% token——助手的调用在各自上下文里，单次便宜；
  但这也说明它**读了 253 个文件却只引用 92 个**，大量阅读对交付物无用。
- 第 9–10 轮使用 `deepseek-v4.1-flash`，第 1–8 轮使用 `deepseek-v4-flash`：
  **跨轮 token 与耗时不可比**，轮内可比。
- 第 1–9 轮的失败**全部来自宿主侧缺陷或夹具设置**；本轮之所以成立，是因为那六处缺陷已逐一修复并各有反向验证。

## 后续：首次 CI 运行暴露的回归

本工作推送后 CI 全红。分类需要先排除干扰：`v0.10.0` 与 `v0.11.0` 两次发布均带 `[skip ci]` 合入，
因此**自 v0.9.0 起 CI 未真正运行过**，本分支是三个版本以来第一次触发。

把失败逐条在干净 `main` 工作树上复跑（`PYTHONPATH` 指向该工作树的 `src`，否则可编辑安装会让
worktree 仍导入主目录的源码，对照无效），得到三类：

| 类别 | 数量 | 处置 |
|---|---|---|
| 本次改动引入的回归 | 13 | 已全部修复 |
| `main` 既有失败（v0.10/v0.11 期间累积） | 8 + 1 个插件分发用例 | 不属本次范围，另行处理 |
| 仅本机环境 | 7 个 GBK 解码 + 17 个 wheel 离线安装 + 1 个可编辑安装版本过期 | 非 CI 问题 |

GBK 一类以 `PYTHONUTF8=1` 复跑全部通过，证明来自本机中文区域设置而非代码。

13 个回归的根因只有两类，都属「改了合同却没同步它的用例」：

1. **ADR-0080 的结算合同变更**（`test_control_model_calls` 2 项）。未知用量改为按**有界预留**计费而非
   全额授予，超预留用量改为**抛错**而非静默降级；这两个用例仍钉着旧行为，而该文件本次并未打开过。
2. **文本与预算算术位移**（其余 11 项）。`_SEARCH_GUIDANCE` 改写后用例仍断言旧句子；
   `PRODUCT_TASK_SCHEMA_VERSION` 由 1 升至 5 而用例被钉成 **4**（差一）；
   `test_in_turn_compaction` 原先**依赖提示噪音**才够到压力阈值，噪音去掉 1,091 token 后压缩不再触发——
   改为由工具输出自身提供压力（`EMIT_UNITS = 1800`），这比依赖提示体积更贴近该用例本意；
   `test_reference_token_budget` 的窄窗口因固定 schema 增加 389 token 而需由 5,000 调至 5,500。

另修正本次提交自身的一处缺陷：`prompt.py` 中那段解释性注释被**重复粘贴了三遍**。

验证：干净全量（`PYTHONUTF8=1`，排除离线不可行的 wheel 用例）后，13 项回归全部消失，剩余失败恰为
上表第二、三类。其中 `test_tui_governance` 的 `TimeoutError` 一度被误记为回归，实为**我自己并行跑
对照测试造成的资源竞争**——单独跑、五个 TUI 文件同跑、以及无并发的干净全量三种情况下均通过。
